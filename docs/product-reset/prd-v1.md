# Social Git product requirements v1

Document version: 1.0.0
Status: implementation baseline for the first self-hosted release.

## Outcome

An operator can deploy Social Git with one Compose/Coolify application, create
the first owner, issue scoped API keys, register multiple accounts, import
owner-authorized sessions through the server-side staging boundary, and use one
stable REST/OpenAPI/MCP interface. The installation includes a control plane,
interactive API explorer, durable actions, signed webhooks, backups, health and
audit evidence. No browser automation or official social developer API is a
runtime dependency.

## Users and primary journeys

1. A self-hoster deploys the documented Compose stack, opens `/app/`, creates
   the sole initial owner, and records recovery prerequisites.
2. The owner registers an immutable native account identity, stages session
   material outside the browser, imports only its one-time handle, and sees the
   verified generation and capability state.
3. An application receives a least-privilege API key, discovers the generated
   contract at `/docs/` or `/openapi.json`, performs reads, queues idempotent
   writes, and observes durable terminal/UNKNOWN state.
4. The owner registers an HTTPS webhook, stores its one-time signing secret,
   and inspects bounded retry/delivery evidence.
5. The owner creates an encrypted recovery set and rehearses restore before an
   upgrade or migration.

## Functional requirements

- One self-hosted tenant with first-run owner setup, HttpOnly browser session,
  CSRF-bound mutations, and tenant-scoped API keys.
- Multiple Reddit accounts with expected-native-identity binding, encrypted
  session/route generations, health, refresh, and revocation.
- Reddit reads and bounded writes exactly as generated by
  `packages/reddit-adapter/src/contract.mjs` and exposed by `src/contract.ts`.
- Opaque caller-driven pagination; no synthesized cursor and no background
  expansion of unsupported data.
- Durable caller-scoped idempotency and action states: queued, running,
  succeeded, failed, action_required, UNKNOWN, and pre-dispatch cancelled.
  UNKNOWN is never retried.
- Signed tenant webhooks with encrypted secrets, redacted listings, bounded
  retries, DNS/private-address denial, and durable attempt history.
- Local CSP-safe API explorer and committed OpenAPI 3.1 document generated from
  `src/contract.ts`; no CDN or hosted documentation runtime.
- X contract visibility is generated from
  `packages/x-adapter/src/admission.mjs`. It remains fixture-only while any live
  admission gate is false; the product must not offer a production connect or
  dispatch path in that state.

## Non-functional requirements

- Clean `docker compose up` deployment and Coolify-compatible Compose topology.
- No Playwright, Selenium, Chromium, CDP, password login automation, CAPTCHA or
  challenge bypass, official social API dependency, proxy rotation, or account
  pooling.
- Secret material is accepted only at bounded custody boundaries, encrypted at
  rest, excluded from logs/responses/backups metadata, and never persisted in
  browser storage.
- Platform workers have no database access, use versioned size-bounded IPC, and
  receive exact account/generation/route/capability bindings.
- Generated contracts, examples, product matrix, tests, and release evidence
  must match the same source registries.

## Explicit exclusions

- Reddit moderation, direct messaging, and comment `more` expansion.
- Any X live production promise until every machine gate and separately
  authorized identity/read/write proof passes.
- Automatic write retries after dispatch, arbitrary webhook destinations,
  automatic remote upgrades, and silent capability emulation.

## Acceptance

Release evidence follows `acceptance.md`: clean install, deterministic tests,
container/Compose checks, restart/backup/restore, scoped-key journeys, tenant
and secret isolation, honest capability reporting, then separately authorized
live smoke. Deterministic evidence alone does not promote a live gate.
